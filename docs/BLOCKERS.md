# BLOCKERS

Những việc cần người dùng, chủ gDesk hoặc khách DanceFITVN quyết định. Orchestrator ghi vào đây rồi làm tiếp bằng dự phòng (08 §5).

Cập nhật 2026-11-16 (P8.6): việc đã xong nằm ở mục 1; việc còn mở xếp theo người phải làm (mục 2–6). Không việc mở nào bị bỏ. Mục "Đề xuất gDesk" ở cuối giữ nguyên.

Tổng: **mở 41** — Người dùng 20, DanceFITVN 3, Backend (gFly) 2, Chủ tài khoản 3, Chủ gDesk 13 · **đóng 9** (U19, U20, B2, D1 đóng tại chỗ trong bảng của mục).

Ưu tiên: **G3a** (khoá `NSFaceIDUsageDescription`) là cần thiết cho bản phát hành iOS; **G1** đứng đầu gDesk vì tvOS (Caches có thể bị xoá → đăng xuất).

- **API (phác thảo, như 06 §3):**
  ```go
  // foundation/platform
  type PhotoPickerDriver interface {
      // PickPhoto shows the picker of one photo over the app and returns at once.
      // done, never nil, runs once on the UI thread with the photo, or an error:
      // one wrapping context.Canceled when the user left the picker. A returned
      // error (core.ErrDuplicate while a picker shows, core.ErrUnsupported) means
      // done never runs. UI thread.
      PickPhoto(opts PhotoOptions, done func(Photo, error)) error
  }
  type PhotoOptions struct {
      MaxSide  int   // longest side handed as it is; larger or not JPEG/PNG → upright JPEG ≤ MaxSide; 0 = 4096
      MaxBytes int64 // a larger file fails with core.ErrInvalid; 0 = 64 MiB
      Camera   bool  // G2b; core.ErrUnsupported until then
  }
  type Photo struct {
      Data []byte // JPEG or PNG
      MIME string // "image/jpeg" or "image/png"
  }
  // bridge/system/photos — UI thread
  type (Options = platform.PhotoOptions; Photo = platform.Photo)
  func Pick(d platform.Driver, opts Options, done func(Photo, error)) error
  ```
  Sửa so với 06 §3 (`Pick(d, PickOptions{Camera, MaxBytes}, done func([]byte, error))`): trả struct `Photo` (thêm trường sau không phá cam kết 1.x, `docs/stability.md`; có `MIME`); thêm `MaxSide` (giới hạn ảnh giải mã — đây mới là thứ giữ bộ nhớ thấp); gDesk không có `core.ErrCanceled` → huỷ bọc `context.Canceled` (như G3).

### G11 — Căn trang 16 KB cho thư viện Android (libmain.so)
- **Lý do:** Google Play bắt mọi app mới và bản cập nhật **target Android 15+** (API 35+; DanceFITVN target 36) phải chạy được trên máy trang bộ nhớ 16 KB, hạn 2025-11-01 (gia hạn tối đa tới 2026-05-31) — đã có hiệu lực; Play Console từ chối bản tải lên có `.so` không căn 16 KB. Trên máy nhân 16 KB, thư viện có segment `LOAD` căn 4 KB không nạp được (Android 15) hoặc chạy ở chế độ tương thích kèm cảnh báo (Android 16+; theo tài liệu Android, chưa kiểm). Căn 16 KB vẫn chạy bình thường trên máy 4 KB (bội số). gDesk tự ghi đã làm: "**16 KB** page alignment (zipalign `-P 16`, as Android 15 requires)" (`kits/cli/README.md:68`; doc `(*builder).android` "aligned for 16 KB pages", `kits/cli/android.go:295-298`) — nhưng `zipalign -P 16` (`android.go:363-366`) chỉ căn **vị trí tệp `.so` trong zip**, không đổi căn segment bên trong ELF. Căn segment do trình liên kết quyết định: `android.go:325` đặt `CGO_LDFLAGS=-Wl,--build-id=sha1`, không có `-z max-page-size`; `cmd/link` của Go cũng không truyền (`grep max-page-size` trong `src/cmd/link/internal/ld` của go1.27.3 → không có); lld của NDK **r27 trở xuống** mặc định 4 KB trên arm64, **r28+** mặc định 16 KB. gDesk chọn `ANDROID_NDK_HOME` trước NDK mới nhất trong `$ANDROID_HOME/ndk` (`android.go:576-578`, `emulator/test.sh:47`) → kết quả phụ thuộc máy build. Máy này đặt `ANDROID_NDK_HOME=…/ndk/26.3.11579264` (r26d, clang/LLD 17.0.2) dù đã cài NDK 30. Đo (2026-11-15, `llvm-readelf -lW`): `dist/android-arm64/DanceFITVN.apk` → 4 `LOAD` `Align 0x1000`; bản phát hành `dist/release/DanceFITVN-1.0.0-1-debugkey.apk` (dự phòng bên dưới) → `0x4000`, `check-android.sh` "LOAD segments aligned to 16 KB or more". Thư viện C thử (`-shared`, aarch64 API 26): r26d `0x1000`, r26d + `-Wl,-z,max-page-size=16384` `0x4000`, r30 `0x4000` có hay không cờ. **jPlayer Mobile:** cùng kiểm (`$JM/scripts/release/check-android.sh:15,149-157`, LOAD ≥ 16 KB) nhưng không gặp lỗi vì build với NDK 30.0.16248370 (`$JM/CLAUDE.md:89`) — mặc định của NDK, không phải của gDesk; không có mục GM nào cho việc này, không dùng `CCC_OVERRIDE_OPTIONS`.
- **Vị trí:** `kits/cli` (cộng một dòng script test); không đổi API.

### G13 — Android: gợi ý nhịp khung cho UI thread (ADPF `APerformanceHint`)
- **Lý do:** P8.4 đo trên Galaxy A17 (Galaxy A17, SM-A175F, MediaTek MT6789, API 36, 90 Hz; `local/p8/perf/report.md` ghi chú 7, 10–14): khung đầu của mỗi lần fling sau ~300 ms không vẽ tốn ~28–32 ms trung vị (paint ~11–13 + present ~16–20 ms; max 32,9–35,9, 3–11/20 khung > 32 ms), khung ổn định 8,4–8,8 ms. Layout 0,04 ms, không cache nào bị bỏ, không dựng lại gì. Nguyên nhân là xung nhịp: sau khoảng nghỉ các nhân ở mức sàn (cpu0 500 MHz/2,0 GHz, nhân lớn 725 MHz/2,2 GHz, `scaling_cur_freq`), UI thread thức trên nhân chưa tăng xung; giữ cả 8 nhân bận thì cùng khung còn **7,0 ms** (paint 1,3 / present 5,6). Chạm thật (`adb input swipe`) có input boost của hệ thống → khung đầu 8,6–14,1 ms, 0 khung > 32 ms (lưu ý: mỗi lệnh `input` khởi JVM ngay trước, cũng làm ấm CPU) → người dùng thật ít gặp hơn nhiều; phần lớn là sản phẩm của fling tổng hợp (`internal/app/devperf.go:156` `flingWindow` gửi down, 6 move, up từ một callback hẹn giờ, Android không thấy chạm). Nhưng input boost không phủ khung không bắt đầu bằng chạm: hoạt ảnh sau timer/kết quả mạng, phím (remote, bàn phím), tick video, khung đầu khi ảnh tải xong. gDesk không báo gì cho hệ thống về công việc mỗi khung: không có `APerformanceHint`/`PerformanceHintManager` trong repo (`grep`), `canvas.RefreshRate` cố định 60 (`bridge/backend/android/window_android.go:365-367`) dù máy chạy 90 Hz. Android có ADPF: `PerformanceHintManager` (Java API 31), NDK `APerformanceHint_*` (API 33) — session cho các thread, mục tiêu mỗi chu kỳ, báo thời lượng thật mỗi chu kỳ → power HAL nâng/hạ xung; API 36 thêm `APerformanceHint_notifyWorkloadIncrease(session, cpu, gpu, id)`, "should be sent shortly before the start of the cycle where the workload is going to change" (NDK 30 `performance_hint.h:340-364`) — đúng ca khung đầu sau nghỉ. Không cần quyền, không đổi manifest. jPlayer Mobile/TV không có đề xuất cùng loại (đã tìm `PerformanceHint`, `ADPF`, `notifyWorkload` trong `docs/`, `CLAUDE.md` của hai repo).
- **Vị trí:** chỉ `bridge/backend/android`; không đổi hợp đồng.
  - Đường khung hôm nay: `(*Driver).postFrame` (`driver_android.go:716-723`) là nơi duy nhất gọi `C.gdesk_post_frame`, một lần tới khi callback về (`framePosted`); `gdesk_post_frame` (`activity_android.go:153-155`) gọi `AChoreographer_postFrameCallback` với `onFrame` (:151, bỏ `nanos`) → `gdeskFrame` (`cgo_android.go:304-313`) → `(*Driver).frame` (`driver_android.go:797-825`) → `drawFront` (:830-839, `EventFrame`: layout, paint, present đều trên UI thread).   ```go

  ```go
  // frameHint decides, from the frames' times alone, what the driver tells Android's
  // performance hint session (ADPF): the work of each frame drawn, the refresh period
  // as its target, and a workload increase before the first frame after an idle spell,
  // when the cores have dropped to their floor clock. It allocates nothing.
  type frameHint struct {
      lastFrame, period int64 // monotonic nanoseconds
      idle              bool
  }
  func (h *frameHint) posted(now int64) (wake bool)              // postFrame: notifyWorkloadIncrease when true (API 36)
  func (h *frameHint) vsync(frameTimeNanos int64) (target int64)  // onFrame: a new target when the period changed, else 0
  func (h *frameHint) drawn(start, end int64) (actual int64)     // after drawFront: reportActualWorkDuration
  // hint_android.go (android && cgo), C helpers, each a no-op without a session:
  //   gdesk_hint_open(tid, targetNanos), gdesk_hint_target(ns), gdesk_hint_report(ns),
  //   gdesk_hint_increase(gpu), gdesk_hint_close()
  ```
